Metodología: Extreme Programming (XP)

Elegida para maximizar la calidad del código mediante prácticas técnicas rigurosas y adaptación rápida a los cambios del entorno.

Prácticas Centrales Implementadas

Debido a la alta complejidad de coordinar microservicios y manejar dinero/transacciones en tiempo real, adoptamos las prácticas de XP para minimizar riesgos técnicos.

🧪

TDD

Desarrollo guiado por pruebas. Ningún microservicio se programó sin antes escribir sus pruebas unitarias (especialmente el algoritmo de relevancia).

👥

Pair Programming

Todo el código crítico (como la lógica de pagos y bloqueo de alimentos vencidos) fue escrito por dos programadores en un mismo teclado para evitar bugs lógicos.

🔄

Integración Continua

Múltiples despliegues diarios a producción mediante pipelines automatizados (CI/CD). Si las pruebas de integración fallaban, el despliegue se detenía.

📦

Entregas Pequeñas

Ciclos de lanzamiento de una semana. Cada iteración añadía valor real y funcional que podíamos probar con tiendas locales en la zona de Sarco.

Rejilla de Cockburn

Clasificación de metodologías según tamaño de equipo y criticidad del sistema.

Lectura de la matriz

Con 4 personas en el equipo de desarrollo y un impacto de dinero discrecional (una falla significa que no se vendió un lote, pero no quiebra el negocio), ResqApp cae en la celda D6.

¿Por qué XP y no Scrum clásico?

  • ✔ Al usar una arquitectura de Microservicios, necesitábamos rigor técnico (CI/CD) extremo, algo en lo que XP es superior a Scrum.
  • ✔ El riesgo del proyecto estaba en los bugs (ej: mostrar productos vencidos) más que en la gestión de tareas. El Pair Programming de XP mitiga esto.

Los 5 Valores aplicados

💬

Comunicación

Diálogos diarios en equipo; el código es documentación viva.

🎯

Simplicidad

Diseñamos la base de microservicios estricta, sin sobreingeniería.

🔁

Feedback

Validación temprana con dueños de comercios cada viernes.

🦁

Coraje

Borramos código y refactorizamos sin miedo gracias al TDD.

🤝

Respeto

Propiedad colectiva del código. Ningún microservicio es "de un solo dueño".
