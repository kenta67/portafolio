Arquitectura: tres capas + descomposición modular

Justificación, características, ventajas, limitaciones y relación con los requerimientos.

¿Por qué es adecuada para ResqApp?

Factor Situación de ResqApp Qué aporta la arquitectura
Características Sistema transaccional: el stock, la entrega y el impacto deben cambiar juntos o no cambiar Una sola base de datos permite una transacción atómica con bloqueo de fila
Usuarios Clientes, comercios y administrador sobre la misma interfaz web Una aplicación con permisos por fila (RLS), sin sistemas separados por rol
Volumen Piloto: 15 a 25 comercios, hasta ~2.500 usuarios diarios, cientos de lotes al día Una base de datos alcanza de sobra; el cuello de botella son las fotos, que van a un CDN
Escalabilidad Crecer por zonas y luego por ciudades La capa de datos está aislada: cambiar de proveedor toca una carpeta. Si un módulo crece, se puede separar después
Mantenimiento Equipo pequeño y rotativo de estudiantes Cada capa en su carpeta y cada módulo con nombre del negocio: se sabe dónde tocar
Separación Reglas de negocio críticas (nunca vencido, descuento mínimo) Las reglas viven en la capa de lógica, sin depender de la pantalla ni de la base
Comunicación Formularios, feed y chat Llamadas directas dentro del mismo proceso (Server Actions): sin red interna ni colas
Seguridad Datos de comercios y conversaciones privadas La interfaz nunca toca la base; el servidor valida todo y la base aplica RLS (defensa en profundidad)

¿Por qué no microservicios?

Con 3 a 5 personas, operar varios servicios con bases de datos separadas multiplica el trabajo, y la entrega necesita una transacción que abarque stock e impacto a la vez.

¿Por qué no SOA?

No hay sistemas corporativos que integrar; SOA resuelve un problema que ResqApp no tiene.

¿Y dirigida por eventos?

El núcleo es transaccional. Los eventos se usan donde sí aportan: tareas programadas y, en la fase 2, notificaciones.

Ventajas

  • • Simple de desplegar: una aplicación y una base de datos.
  • • Costo cero en el piloto con planes gratuitos.
  • • Reglas de negocio probables sin levantar la base de datos.
  • • Evoluciona: un módulo se puede extraer a un servicio si algún día lo necesita.

Posibles limitaciones

  • • Se despliega todo junto: un error en un módulo afecta a toda la aplicación.
  • • Parte de la lógica crítica está en funciones SQL (la entrega), repartida entre TypeScript y PL/pgSQL.
  • • Dependencia de Supabase, mitigada con la capa de repositorios.
  • • Escala vertical: para cientos de miles de usuarios habría que separar lecturas o módulos.
